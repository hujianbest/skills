# Chapter 16: 修改现有的代码 (Modifying Existing Code)

## Core Idea
成熟系统的设计更多由演化中的每次修改塑造，而非初始构想。修改代码时最容易滑入战术心态（"我能做的最小改动是什么？"）——要保持战略: 每次修改后，系统应近似于"从一开始就带着这次修改去设计"的样子。

## Frameworks Introduced
- **修改时的战略原则**:
  - 抵制最小改动诱惑: 每次"最小修改"都注入几个特殊情况/依赖，累积成设计劣化
  - 动手前先问: **结合这次变更，当前设计还是最优吗？** 不是 → 重构到最优再改
  - 每次进代码都顺手至少改进一点设计——"如果你没有让设计变好，你多半正在让它变坏"
  - 现实折衷: 正确重构 3 个月 vs 快修 2 小时、或重构造成大量跨团队不兼容——可妥协，但要问"在当前约束下这是我能做到的最好吗？"并争取事后补偿时间；组织应常态预留一小部分精力做清理
- **注释维护三术**:
  1. **贴近代码 (keep comments near code)**: 注释离代码越远越不会被更新。方法接口注释放**代码文件**里紧贴方法体（而非 .h 头文件）——用户应从 Doxygen/Javadoc/IDE 获取文档，不必翻源文件；实现注释**下推到最窄作用域**（每阶段的注释放该阶段代码上方），而非全堆在方法顶部（顶层只留总体策略三行）
  2. **避免重复 (avoid duplication)**: 每个设计决策**只记录一次**，放在最显眼的单一位置；他处放短引用（"See the comment in xyz"）。引用失效会自暴露（找不到注释），重复文档失效则无感——更危险。不跨模块复述他人的设计决策（调用点不解释被调方法内部）；外部已有文档（HTTP 协议、用户手册）只引用不复制: "Implements the Foo command; see the user manual"
  3. **提交前扫 diff (check the diffs)**: 提交前几分钟通览全部改动，确认每处改动都在注释中正确反映——顺带抓出遗留调试代码、忘改的 TODO
- **注释属于代码，不属于提交日志**: 描述"为什么需要这次改动"的信息若只写在 commit message 里，后来者不会去翻仓库日志，甚至可能无知地撤销你的修复、重新引入 bug——先写进代码，commit message 可附副本
- **越抽象越易维护**: 高层/抽象注释不随代码细节微调而失效（只有整体行为变化才波及）——与 ch13 呼应：最有用的注释恰好也最好维护

## Key Concepts
- "最小改动"心态的根源: 对陌生代码的畏惧（大改动怕引入 bug）——但恰恰是这种畏惧让系统永远烂下去
- 注释过时的真正代价: 读者一旦发现多处过时就**不再信任任何注释**

## Key Takeaways
1. 修改 = 重构的窗口期；带着"假装从零设计"的标准收尾
2. 接口注释贴着实现放；实现注释放最窄作用域；一处决策一处文档
3. 提交 diff 是注释时效性的最后一道关卡
