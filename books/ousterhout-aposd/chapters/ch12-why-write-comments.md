# Chapter 12: 为什么写注释？四个借口 (Why Write Comments? The Four Excuses)

## Core Idea
注释不是代码的附属品，而是**抽象的必要组成**——没有注释就无法隐藏复杂性。写注释（若方法得当）本身就是改进设计的过程。

## Frameworks Introduced
- **逐条驳斥四个借口**:
  1. **"好代码自文档化"**: 美味的神话。代码只能表达接口的形式部分（签名）；非形式部分（方法整体行为、参数语义、前置条件、设计理由）**只能**用注释表达。若用户必须读实现才能用方法，就没有抽象可言。期望用户读实现还会诱导向浅方法的方向退化
  2. **"没时间写注释"**: 投资心态的反面。输入代码的时间约占开发 10%；注释与代码等量也只增加约 10% 开销，收益迅速覆盖成本。最关键的类/方法顶层注释本就该作为设计过程的一部分来写（ch15），立即回本
  3. **"注释会过时、变成误导"**: 大的代码改动才需要大的注释改动，而前者比后者更耗时；避免重复、贴近代码（ch16）+ 代码审查能把过时注释压到最低
  4. **"见过的注释都毫无价值"**: 四条中最有理——因为大多数注释写法错误（重复代码、复述名字）；这是可解的技能问题（ch13）
- **好注释的本质**: 捕获**设计者头脑中有、而代码表达不出的信息**——从低层（某硬件怪癖）到高层（类存在的基本原理）。即使原作者几周后回来也靠它

## Key Concepts
- 注释如何对抗复杂性的三种表现: 降低**认知负荷**（要的信息直接给、无关的直接忽略）、消除**未知的未知**（澄清系统结构、指明改动相关处）、阐明**依赖**并填补**模糊**
- 注释用自然语言书写: 不如代码精确，但表达力更强——得以创建简单直观的描述

## Key Takeaways
1. 想用抽象藏复杂性，注释必不可少——抽象的"简化视图"由注释补全
2. 四个借口全部站不住，第 4 个指向的是写法问题而非注释本身
3. 注释写得好的系统里，写注释甚至是件有趣的事（ch15）
