# Chapter 11: 设计它两次 (Design It Twice)

## Core Idea
软件设计很难，第一个想到的方案几乎不可能是最佳方案。为每个主要设计决策考虑**多个备选方案**并对比优劣——设计两次（或三次）。这既是获得更好设计的途径，也是训练设计眼光的方法。

## Frameworks Introduced
- **Design it twice 工作流**:
  1. 为模块接口草拟 2-3 个**彼此根本不同**的方案（即使确信只有一个合理方案，也强行设计第二个——分析它的弱点极具启发性）
  2. 列出每个方案的优缺点。接口的首要标准: **高层软件的易用性**；其次: 接口更简单？更通用？实现更高效？
  3. 选择最佳——可能是其一，也可能是多个方案特征的组合；全不满意时，用已发现的问题驱动**新方案**
- **适用层级**: 选接口、选实现（text 类实现可选行链表/固定字符块/gap buffer——实现期目标换成简单性+性能）、选 UI 功能、划分子系统……处处可用
- **成本**: 小模块一两个小时，对比数天的实现期——必赚

## Key Concepts
- **聪明人的陷阱**: 从小靠第一灵感就能拿高分的人养成坏习惯；终会遇到第一灵感不够用的难题——大型软件设计必属此类，**没有人聪明到一次做对**。"尝试多种设计=不聪明"是潜意识谬误：不是你不够聪明，是问题真的难
- **副产品**: 设计-比较的循环会教你看清什么让设计变好变坏，长期形成快速排除坏设计的能力

## Worked Example
text 类接口的三方案演化:
- 方案 A 面向行: 高层软件在部分行/跨行操作（剪贴选区）时要拆行合行
- 方案 B 面向单字符: 改多字符要写循环，低效
- 两案的共同红旗: **既然存在 text 类，就该由它处理全部文本操作** → 高层操作既不总对应单字符也不总对应整行 → 驱动出方案 C 面向区间 (range-oriented): `insert(pos, string)` / `delete(start, end)`——前面所有问题一并消失

## Key Takeaways
1. 每个重大决策强制产出多个 radically different 的备选再选
2. 备选方案的缺点清单比优点清单更有教学价值
3. 所有备选都不佳时，别将就——让痛点指出新方向
