# Chapter 20: 设计性能 (Designing for Performance)

## Core Idea
干净设计与高性能**兼容**——通常简单代码本来就更快（无特判、深类每次调用干更多活、层穿越少）。性能优化的关键仍是简单性: 先做自然高效的设计，慢了先测量，最后才围绕关键路径重构。

## Frameworks Introduced
- **如何看待性能的两个极端及中道**:
  - 每条语句都优化 → 开发慢、复杂性暴涨、多数"优化"无效
  - 完全不管 → 效率低下遍布代码，系统慢 5-10 倍，"千刀凌迟"式死法——之后无从下手（没有任何单点改进有显著影响）
  - **中道**: 用性能常识选**"自然高效"且干净简单**的设计
- **昂贵操作清单** (建立意识): 网络往返（数据中心 10-50µs = 数万条指令；广域 10-100ms）；磁盘 I/O 5-10ms（闪存 10-100µs）；动态内存分配（分配+释放+GC 开销可观）；**cache miss**（DRAM→片上缓存 = 数百条指令，很多程序的性能由它决定）
  - 学习途径: **microbenchmark**（RAMCloud 自建微基准框架，新增一条基准只需 5-10 分钟）
  - 应用例: 键值查找选哈希表而非有序 map（快 5-10 倍且同样简单）；结构体数组直接内嵌而非指针数组（一次分配）
- **何时为性能加复杂性**: 高效方案仅增少量**隐藏的**复杂性（不影响接口）→ 可取；增大量实现复杂性或弄复杂接口 → 先简单后优化。**但有明确测量证据表明性能关键时，直接上快方案**（RAMCloud 绕过内核直接对话网卡——一个大的根本决策做对，其余部分得以保持简单）
- **修改前必测量 (measure before modifying)**: 程序员的性能直觉**不可靠**（老手也一样）。测量的两目的: ①定位系统耗时最多的少数具体位置（只测顶层"系统慢"没有用）②建立基线——改完复测，无显著提升就回退（除非它同时让系统更简单）；"不能带来显著加速的复杂性没有保留价值"
- **围绕关键路径设计 (design around the critical path)**——重构慢代码的方法:
  1. 问: 常见情况下完成任务**最少要执行多少代码**？无视现有结构，想象一个只含关键路径的理想方法（全部代码在一个方法里、无特判、用最方便的数据结构、可合并多个变量）——"**理想 (the ideal)**"
  2. 理想代码可能不现实，但它是**最简最快的上限**；寻找尽可能接近理想、同时结构干净的新设计（允许少量额外代码换取干净抽象，如哈希表类的一次方法调用）——"几乎总能找到既干净又极接近理想的设计"
  3. **从关键路径上除掉特判**: 理想形态 = 开头**一个 if 检测出全部特殊情况**，正常路径零额外检查，特判走关键路径之外的旁路（旁路按简单性构造，不必按性能）
  4. 优先找**根本性修复** (fundamental fix): 缓存、换算法/数据结构——有则用常规设计技术实现

## Worked Example
RAMCloud Buffer 类 ~2 倍提速（+代码缩小 20%）:
- 原关键路径 `alloc → allocateAppend → Allocation::allocateAppend`: 三层**同签名**浅方法（红旗）、6 个逐一检查的特判（有无 allocation、空间够不够查了三遍、新空间是否与末 chunk 相邻再合并）
- 重构: 引入实例变量 `extraAppendBytes`（末 chunk 后紧邻的可用空间；无空间/末 chunk 非内部/无 chunk 时为 0）——**一个变量把三种特殊情况折叠为一次判断**；整个路径收进单个方法
- 结果: 1 字节 append 8.8ns → 4.75ns；构造+append+销毁 24ns → 12ns；类反而更小更好读
- 教训: 浅层与特判既是设计问题也是性能问题；删除它们一举两得

## Key Takeaways
1. 简单 ≈ 快；先把设计做干净，多数时候性能就够了
2. 性能问题三步走: 常识设计 → 测量定位 → 关键路径重构（理想代码法）
3. 无测量的优化是被禁止的；无收益的复杂性必须回退
