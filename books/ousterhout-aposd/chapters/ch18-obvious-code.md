# Chapter 18: 代码应该是显而易见的 (Code Should be Obvious)

## Core Idea
"显而易见" = 读者不加思索快速阅读，对代码行为/含义的**第一猜测就是对的**。这是对"模糊性"和"未知的未知"的终极解药。判断权在读者: 有人说你的代码不明显，它就不明显。

## Frameworks Introduced
- **让代码更明显的手段**:
  - 好名字 (ch14) + 一致性 (ch17)——两大支柱
  - **明智使用留白**: 参数文档项之间空行分隔（参数个数、名称一目了然）；方法内用**空行分隔主要代码块**——块前注释+空行的组合尤其有效（空白让注释更醒目）；语句内部空格澄清结构 (`for (int pass = 1; pass >= 0 && !empty; pass--)` 好于无空格版)
  - **注释补偿**: 无法避免的不明显代码（如事件驱动）用注释补足缺失信息——站在读者角度想"什么会让他困惑"
- **让代码不明显的典型事物**:
  - **事件驱动编程 (event-driven programming)**: 控制流难以跟随——handler 从不被直接调用，由事件模块经函数指针/接口间接调用，具体调谁取决于运行时注册 → 推理困难。补偿: 每个 handler 的接口注释写明**何时被谁调用**（"本方法在分发线程中由 transport 调用，当传输级错误阻止 RPC 完成时"）。红旗: 不明显代码
  - **通用容器 (generic containers)**: `return new Pair<Integer, Boolean>(currentTerm, false)` —— 调用方只能 `result.getKey()/getValue()`，语义全无 → 定义专用类/结构，元素有实义命名、声明处可加文档。通则: **软件为易读而设计，不为易写**——作者多花几分钟定义专用容器，读者省无数次困惑
  - **声明与分配类型不一致**: 声明 `List` 实际 `ArrayList`——看到声明的人被误导（性能/线程安全属性不同）→ 声明与分配匹配
  - **违反读者期望**: 如 `main` 里 new 一个对象就返回，读者默认程序退出——但 RaftClient 构造器创建了后台线程继续运行。代码符合惯例才最明显；不符合时必须文档化
- **信息论视角理解"明显"**: 不明显 = 读者缺少理解代码所需的重要信息。三种补救: ①减少所需信息量（抽象、消灭特殊情况——上策）②复用读者已有的知识（惯例、期望）③把重要信息呈现给读者（好名字、关键注释）

## Key Takeaways
1. 目标状态: 读者快速扫读、第一猜测正确、无需查文档
2. 代码评审是"明显性"的检验标准——读者说不明显就不明显，别争辩，去改代码或注释
3. 为易读设计优先于为易写设计
