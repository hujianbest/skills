# Chapter 14: 选择的名字 (Choosing Names)

## Core Idea
命名是被低估的设计活动: 好名字是一种文档——降低其他文档需求、让错误更容易暴露。好名字的两属性: **精确 (precise)** 与 **一致 (consistent)**。

## Frameworks Introduced
- **命名的目标——在读者脑中成像**: 看到孤立的名字（不见声明、文档、用法），能多准确地猜到它指什么？好名字传达实体是什么、以及同样重要的是**不是什么**。名字是抽象: 聚焦最重要的方面、省略次要细节（超过 2-3 个词就笨重）
- **精确**: 最常见病是**太泛**——红旗: 含糊名字。"count of what?" `getCount()` → `getActiveIndexlets()`；x/y（像素坐标还是行内字符位置？）→ `charIndex`/`lineIndex`；`blinkStatus`（布尔名不该叫 status）→ `cursorVisible`（**布尔名应为谓词**）；哨兵值 `VOTED_FOR_SENTINEL_VALUE` → `NOT_YET_VOTED`
  - 例外: 短循环变量 i/j 可以（整个使用范围一眼可见时）；名字也可能**太具体**: `delete(Range selection)` 的参数被选区概念绑死 → `range`
  - **红旗: 难以取名**——找不到精确、直观、不长的名字，往往说明实体本身定义不清（比如一个变量想代表好几件事 → 拆成多个变量）。取名过程本身能暴露设计弱点
- **一致 (consistency)**: 三要求——①该用途永远用这个通用名 ②这个通用名绝不用作其他用途 ③**用途足够窄，保证同名变量行为相同**（Sprite 文件系统 bug 正是违反③: block 既指文件内逻辑块又指磁盘物理块）。需要多个同类变量加前缀: `srcFileBlock` / `dstFileBlock`；循环约定: 最外层永远 i、嵌套永远 j
- **命名 vs 距离**: 名字声明与使用距离越远，名字应越长（Gerrand 语，作者认同）

## Key Concepts
- **可读性由读者裁决**: Go 社区鼓励单字母短名（"长名遮蔽代码"），作者不完全同意但承认: 只要读者觉得易读就好；收到"代码难懂"的抱怨就该调整
- 一次坏命名的代价可以极大（见案例），"差不多贴近"不够——多花一点时间取**精确、无歧义、直观**的名字

## Worked Example
作者修过的最难的 bug（耗时 6 个月）: Sprite OS 文件数据块莫名清零。根因: `block` 一名两用（文件内逻辑块号 / 磁盘物理块号），某处逻辑块号被误当物理块号用，无关磁盘块被零覆盖。多名高手反复读代码都无感——看到 `block` 就反射性假设它是"对的那种块"。若当时命名为 `fileBlock`/`diskBlock`，错误几乎不可能发生——程序员一看就知道 fileBlock 不能用在那个位置。

## Key Takeaways
1. 名字是读者对代码的第一份（且最便宜的）文档
2. 布尔名用谓词；太泛的名字加"of what"
3. 每个常见用途定一个全局通用名，绝不挪用
4. 取名困难是设计问题的探测器，先修设计再取名
