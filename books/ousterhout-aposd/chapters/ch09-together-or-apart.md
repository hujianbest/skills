# Chapter 9: 在一起更好还是分开更好？ (Better Together Or Better Apart?)

## Core Idea
"两个功能放一起还是分开"是软件设计最基本的问题之一。判据不是组件大小，而是**整体复杂性与信息隐藏**——细分本身就会制造新复杂性（组件数、接口数、管理代码、分离、重复），只有相关信息共享/简化接口/消除重复时才值得合并。

## Frameworks Introduced
- **细分的隐藏成本**（subdivision costs）:
  1. 组件数量本身：难以追踪、难以找到目标组件
  2. 更多接口：每个新接口都是复杂性
  3. 管理组件的额外代码（原来一个对象，现在要管多个）
  4. **分离 (separation)**: 组件真正独立→分离好；有依赖→开发者在组件间来回跳，甚至不知道依赖的存在（→ bug）
  5. **重复 (duplication)**: 原来一份的代码要在每个组件里出现
- **相关的迹象**（何时该合并）:
  - 共享信息（如都依赖某文档语法）
  - 总是一起被使用（**且双向成立**——反例: 块缓存总用哈希表，但哈希表用途广得多 → 应分开）
  - 概念上重叠（同属一个更高级类别：子串搜索+大小写转换 ⊂ 字符串操作）
  - 不看其中一个就难理解另一个
- **合并的三大判据**:
  1. **信息共享则合并**: HTTP "读请求"与"解析请求"必须懂同一格式 → 一处实现（ch5 案例）
  2. **能简化接口则合并**: 合并后中间接口消失（HTTPRequest 字符串传递）；功能合并还能自动化部分行为让多数用户无感（FileInputStream+BufferedInputStream 合并则用户永远不必知道缓冲存在）
  3. **消除重复则合并**: 相同代码模式反复出现 = 没找到正确抽象（红旗: 重复）。方法: 提取成方法（片段长+签名简单才划算）；或重构使代码只在一处执行（多出口清理逻辑可用 goto 收敛到方法尾——受控使用）
- **通用与专用分离则拆开** —— 红旗: **专用-通用混合 (special-general mixture)**
  - 含多用途机制的模块只提供通用机制；专用代码上提到更高层（与用例同层的模块）
  - 系统下层通用、上层专用；遇到"同一抽象既有通用又有专用特性"的类，考虑拆成"通用层 + 叠在上面的专用层"

## Worked Example
1. **插入光标 + 选区**: 总一起操作（点击拖拽同时设置二者）→ 一个团队合并管理 → 结果尴尬：高层仍要当两个实体分别操作，实现反而更复杂（布尔标志+选区端点间接推光标位）→ **拆开**: 引入通用 `Position` 类，选区=两个 Position，光标=一个 Position——接口更简、实现更直、Position 在项目中别处复用。"相关"不足以合并，要问合并后是否真的更简
2. **日志类**: 把一行 log 调用抽成 NetworkErrorLogger 类的多个静态方法——每个方法一行代码、只在一处调用、读调用点必翻方法、读方法必翻调用点 → **消除该类，log 语句就地写**
3. **撤销机制（拆开的正面案例）**: 通用核心（History 类: addAction/addFence/undo/redo + Action{undo,redo} 接口）与专用动作（UndoableInsert/UndoableSelection...，在各自模块内实现）与分组策略（高层 UI 决定 fence 位置）三者在不同地方实现，互不知晓彼此。关键决策 = 把通用部分单独成类；注意细则: **同一机制**的专用/通用要分开，但**一个机制**的专用代码与**另一机制**的通用代码同住常常合理（text 类里放 UndoableInsert）

## 拆分与合并方法（9.8）
- **长度本身几乎不是拆分方法的理由**；开发者普遍拆得过细。几百行、签名简单、可读的方法是**深**方法，很好
- 拆法一（好）: **提取子任务**——子方法与父方法其余部分干净分离（读子不必懂父、读父不必懂子实现），子方法相对通用。若拆完要在父子间来回翻看才能理解 → 红旗"**连体方法 (conjoined methods)**"，拆错了
- 拆法二: **按功能分成两个方法**——仅当原方法接口因做多件不相关的事而过复杂；新方法接口应更简；多数调用者只需其一，否则更糟
- 合并方法的好处: 两个浅方法→一个深方法、消除重复、消除依赖与中间数据结构、更好封装、更简接口
- 方法设计第一原则: 每个方法做一件事并**做完**；接口远简于实现（深）

## Key Takeaways
1. 拆或不拆，唯一裁判是复杂性：最好的信息隐藏、最少的依赖、最深的接口
2. 别被"相关"迷惑——光标和选区相关但该分开；读+解析看似两步但该合并
3. "一行方法"、"包装类"式的抽取若只增加间接层，删掉它
4. 通用机制里混专用代码是双输：机制复杂化 + 信息泄漏
