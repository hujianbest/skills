# Chapter 17: 一致性 (Consistency)

## Core Idea
一致性 = 相似的事用相似的方式做、不同的事用不同的方式做。它创造**认知杠杆**: 学会一处即可安全推及他处——降低复杂性与出错率。一致性也有反面: 把不同的事强行同化会制造混乱。

## Frameworks Introduced
- **一致性的收益**: 认知杠杆（一处学会处处适用，安全假设）+ 减少错误（不一致时两个本不同的情形看似相同，读者凭熟悉模式做出错误假设）
- **一致性适用的层面**:
  - **名字** (ch14)
  - **编码风格**: 缩进、花括号、声明顺序、命名、注释、危险语言特性的限制
  - **接口**: 同一接口的多种实现——懂一个实现即懂全部
  - **设计模式**: 用公认方案（如 MVC）解决公认问题——实现更快、读者更容易懂
  - **不变量 (invariants)**: 变量/结构恒真的属性（"每行必以换行符结尾"）——减少特殊情况、简化推理
- **如何建立与保持一致性**:
  1. **写成文档**: 全局约定放 Wiki 显眼处，新人必读、老人定期回顾；局部约定（不变量）写在代码中合适位置——不写下来别人就不会遵守
  2. **机械执行 (enforce)**: 人记不住约定 → 写检查工具，不通过不许提交（案例: 换行符约定 → 提交前钩子脚本检出 CR 即拒绝，还可修复受损文件；新人的"车祸期"立即消失）。代码审查做第二道防线——评审越挑剔，团队学约定越快
  3. **入乡随俗 (When in Rome...)**: 最重要的元约定。改新文件先环顾: 公有在前还是私有在前？方法排序？camelCase 还是 snake_case？看到"疑似约定"就跟随；做设计决策前先找项目里有没有同类先例
  4. **别改既有约定**: "我有更好主意"不是引入不一致的理由——一致性的价值几乎总大于方法优劣之差。例外条件（两条都为 yes 才升级）: ①有建立旧约定时不存在的重要新信息 ②新方法好到值得更新所有旧用法；升级要彻底（不留旧痕迹），且仍有他人重新引入旧法的风险
- **走得太远**: 一致性只在不同事物被强同化时失效——不同事物用了相同变量名、不适配的设计模式被硬套。"看起来像 x 就真是 x"的信心才是一致性的价值所在

## Key Takeaways
1. 一致性是投资心态: 约定、工具、评审都要额外投入，回报是代码显而易见
2. 约定不落纸面等于不存在；落了纸面没有工具强制也会溃散
3. 修改代码时"环顾四周"比"个人最佳实践"更重要
