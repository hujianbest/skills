# Chapter 1: 介绍 (Introduction — It's All About Complexity)

## Core Idea
软件设计的核心问题只有一个：复杂性 (complexity)。编写软件的最大限制不是机器，而是我们理解所创建系统的能力。全书围绕一个问题展开：如何在整个软件生命周期中用复杂性来指导设计。

## Frameworks Introduced
- **两种对抗复杂性的通用方法 (Two general approaches)**
  - 消除复杂性：让代码更简单、更明显（消除特殊情况、一致地使用标识符）
  - 封装复杂性：即模块化设计 (modular design)，把系统拆成相对独立的模块，程序员一次只面对一小部分复杂性
  - 何时用：两者并行，模块化是全书主体（第 4-10 章）

## Key Concepts
- **复杂性不可避免地递增**：程序越大、参与人越多，管理复杂性越难；更简单的设计只是让系统在复杂性压垮你之前能建得更大
- **软件设计是贯穿全生命周期的连续过程**：软件足够可塑，设计与实现可交替进行，这区别于桥梁等物理系统
- **瀑布模型 (waterfall model) 对软件失效**：初始设计必然有大量问题，且在实现进行到一定程度后才暴露；无法在中途容纳重大设计变更，导致复杂性爆炸
- **增量开发 (incremental approach)**：每次设计+实现+评估一小部分功能，迭代暴露并修复设计问题
- **设计永远"未完成"**：增量开发意味着持续重新设计；应始终寻找改进设计的机会

## Mental Models
- 想软件设计如写文章：草稿 → 反馈 → 重写的迭代过程（CS 190 课程即如此教学）
- 把设计原则当作"比较设计备选方案的标尺"，而非保证产出最佳设计的配方

## Anti-patterns
- **把设计一次性前置（瀑布式）**：大型软件系统无法在构建前充分可视化，初始设计必然有缺陷
- **"能跑就行"心态**：见第 3 章战术编程

## Key Takeaways
1. 用复杂性作为设计的指南针：任何设计决策都问"这会增加还是降低系统复杂性"
2. 设计是持续活动，不是项目初期的阶段
3. 学会识别红旗 (red flags)：看到红旗就停下来寻找消除它的替代设计；尝试的替代方案越多，学到越多
4. 一切原则都有例外，把任何设计思想推向极端都会变坏；好设计是竞争性思想之间的平衡
5. 书中示例为 Java/C++，但思想适用于函数、子系统、服务等一切"模块"
