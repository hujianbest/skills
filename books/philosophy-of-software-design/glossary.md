# Glossary — A Philosophy of Software Design

- **Abstraction 抽象** — 实体的简化视图，省略可安全忽略的细节、保留重要信息；模块以接口形式提供抽象 (Ch 4)
- **Aggregation (exception) 异常聚集** — 用单个 handler 在能捕获最多异常的位置（通常高层）处理多个异常 (Ch 10)
- **Back-door leakage 后门泄漏** — 知识未出现在接口中却反映在多个模块里（如两个类共享文件格式知识），比接口泄漏更隐蔽 (Ch 5)
- **Change amplification 变更放大** — 看似简单的变更需要修改多处代码；复杂性三症状之一 (Ch 2)
- **Classitis 类炎** — "类越多越好"的综合征，导致大量浅类与接口爆炸 (Ch 4)
- **Cognitive load 认知负荷** — 完成任务所需掌握的知识量；复杂性三症状之一 (Ch 2)
- **Comments-first 先写注释** — 类注释→方法注释+签名→变量注释→方法体的开发顺序，文档即设计工具 (Ch 15)
- **Complexity 复杂性** — 任何使软件系统难以理解和修改的结构性因素；C = Σ cp·tp（按开发时间加权）(Ch 2)
- **Conjoined methods 连体方法** — 两个方法互相依赖到不看对方实现就无法理解；拆分不当的红旗 (Ch 9)
- **Consistency 一致性** — 相似的事以相似方式做、不同的事以不同方式做；创造认知杠杆 (Ch 17)
- **Context object 上下文对象** — 集中存放系统全局状态以消除传递变量的对象，每系统实例一个 (Ch 7)
- **Deep module 深模块** — 功能强大而接口简单的模块；接口=成本，功能=收益 (Ch 4)
- **Define errors out of existence 定义错误不存在** — 重定义 API 语义使正常行为覆盖所有情况、无需异常 (Ch 10)
- **Dependencies 依赖** — 一段代码无法被孤立理解/修改的关系；复杂性两大成因之一，不可全消只可简化 (Ch 2)
- **Design it twice 设计两次** — 每个重大设计决策强制对比多个根本不同的备选方案 (Ch 11)
- **Dispatcher 分派器** — 依据参数选择调用目标的方法；同签名但有真实贡献，非直通 (Ch 7)
- **Information hiding 信息隐藏** — 模块封装设计决策于实现中、不暴露于接口；Parnas 1972 (Ch 5)
- **Information leakage 信息泄漏** — 同一设计决策反映在多个模块中；最重要的红旗之一 (Ch 5)
- **Invariants 不变量** — 变量/结构恒真的属性，减少特殊情况 (Ch 17)
- **Masking (exception) 异常屏蔽** — 低层检测并消化异常，高层无感知；类因此更深 (Ch 10)
- **Modular design 模块化设计** — 将系统分解为相对独立、各自隐藏复杂性的模块 (Ch 1, 4)
- **Obscurity 模糊性** — 重要信息不明显；复杂性两大成因之一，常与依赖相伴 (Ch 2)
- **Obvious (code) 显而易见** — 读者快速阅读时第一猜测即为正确；设计的高目标 (Ch 2, 18)
- **Overexposure 过度暴露** — 常用功能强迫用户了解罕见功能 (Ch 5)
- **Pass-through method 直通方法** — 除转发给同签名方法外无贡献；相邻层抽象相似的信号 (Ch 7)
- **Pass-through variable 传递变量** — 穿透一串用不到它的方法签名的变量 (Ch 7)
- **Pull complexity downwards 复杂性下拉** — 模块开发者内部消化难题，让接口比实现更简单 (Ch 8)
- **Red flags 红旗** — 提示设计可能有问题的信号；全书 14 个（见 cheatsheet）(各章)
- **Shallow module 浅模块** — 接口复杂度相对其功能过高，几乎不隐藏复杂性 (Ch 4)
- **Somewhat general-purpose 适度通用** — 功能反映当前需求、接口不反映；通用接口反而更简单 (Ch 6)
- **Special-general mixture 专用-通用混合** — 通用机制中混入面向特定用例的代码 (Ch 9)
- **Strategic programming 战略编程** — 以长期结构为首要目标、持续投资设计的心态 (Ch 3)
- **Tactical programming 战术编程** — 以"尽快让功能跑起来"为焦点的心态；复杂性之源 (Ch 3)
- **Tactical tornado 战术龙卷风** — 高产但完全战术式的程序员，留下大量维护债务 (Ch 3)
- **Temporal decomposition 时间分解** — 按操作执行时间顺序而非知识划分模块结构；泄漏温床 (Ch 5)
- **Unknown unknowns 未知的未知** — 不清楚要改哪些代码/需要什么信息；三者中最糟症状 (Ch 2)
- **Zero tolerance 零容忍** — 对每次引入的小复杂性一律不容忍的态度 (Ch 2, 3)
