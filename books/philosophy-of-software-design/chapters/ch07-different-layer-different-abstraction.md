# Chapter 7: 不同的层，不同的抽象 (Different Layer, Different Abstraction)

## Core Idea
设计良好的系统中，每层都提供与上下层**不同**的抽象（文件系统：文件字节流 / 块缓存 / 设备驱动；TCP：可靠字节流 / 尽力而为的包）。**相邻层抽象相似是类分解有问题的红旗**，典型形态：直通方法、装饰器、传递变量。

## Frameworks Introduced
- **直通方法 (pass-through method)** ——红旗
  - 定义: 除调用另一个签名相似/相同的方法外几乎什么都不做。学生项目一例：15 个公有方法中 13 个是直通
  - 危害: 类变浅（接口复杂度+，功能+0）、类间依赖（底层签名一改全得跟着改）、暴露职责混乱
  - 处方 (图 7.1 四选一): ①让调用者直接调底层类（高层甩掉该职责）②在类间重新分配功能 ③无法解缠则合并类
- **接口重复何时 OK**: 每个新方法都贡献显著功能时。两例:
  - **分派器 (dispatcher)**: 用参数选择调用哪个方法——同签名但贡献了"选择"功能
  - **同接口多实现**（如磁盘驱动）: 学一个实现即可推及全部——降低认知负荷；它们同层且互不调用
- **装饰器 (decorator/wrapper) 的陷阱**: 装饰器天生跨层复制 API、充满直通方法、浅。创建装饰器前先问四个替代方案:
  1. 能否把新功能直接加进底层类？（新功能相对通用/与底层逻辑相关/大多数使用者也要用——如缓冲之于 I/O）
  2. 专用功能能否并入其用例？
  3. 能否与现有装饰器合并成一个更深的装饰器？
  4. 新功能真的需要包装底层吗？能否做成独立类？（如滚动条 vs 窗口）
- **接口 ≠ 实现**: 类的内部表示应与接口抽象**不同**，否则类不够深。例: text 类内部按行存储，但接口面向字符区间（insert 任意含换行的字符串）——行拆分/合并的复杂性被封进类内
- **传递变量 (pass-through variable)** ——另一种跨层 API 复制: 变量穿透一长串用不到它的方法签名（如 cert 从 main 穿到 m3）
  - 处方: ①已有共享对象则存入 ②全局变量（几乎总是更糟: 无法同进程多实例、测试困难）③**上下文对象 (context object)**——作者最常用: 存放全部全局状态（配置/共享子系统/计数器），每系统实例一个；引用存进各主要对象，仅在构造函数中显式出现。缺点: 变量本身有全局变量的通病（存在感不明、易变大杂烩、线程安全——最好不可变），但没有更好解

## Key Concepts
- **基础设施净收益法则**: 每个接口/参数/函数/类/定义都是开发者要学的复杂性；它必须消除比它引入的复杂性**更多**才有净收益

## Worked Example
`TextDocument` 类几乎全由直通方法构成（getLastTypedCharacter、insertString 等全部转发给 textArea）→ 职责在 TextDocument/TextArea/TextDocumentListener 三类间交织 → 解法：在类间搬移方法、三类并两类，职责清晰分离。

## Key Takeaways
1. 沿一条操作穿层而下，抽象应随每次调用改变；没变就是红旗
2. 看到直通方法就问：这几个类各自到底负责什么抽象？
3. 装饰器模式在语法上方便、在设计上往往浅——先穷尽替代方案
4. 传递变量的最实用解是 context 对象，但要警惕它退化成数据大杂烩
