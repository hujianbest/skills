# Chapter 3: 工作代码是不够的 (Working Code Isn't Enough — Strategic vs. Tactical Programming)

## Core Idea
决定设计质量的最重要因素是你编程时的心态：**战术编程**（尽快让功能跑起来）几乎不可能产出好设计；**战略编程**（首要目标是出色的设计，代码能工作是副产品）前期稍慢、长期反而更快。

## Frameworks Introduced
- **战术编程 (tactical programming)**
  - 特征：以"让某个功能尽快工作"为焦点，为速度容忍少量复杂性和 kludge
  - 恶性循环：复杂性开始引发问题 → 修 bug 比重构更要紧 → 打补丁 → 更多复杂性 → 代码成泥球，清理需数月 → 只能继续战术
- **战术龙卷风 (tactical tornado)**: 多产程序员，出代码速度远超他人，完全战术式工作；管理层可能视为英雄，但留下一地废墟，后续维护者（真正的英雄）反而显得慢
- **战略编程 (strategic programming)**
  - 核心信条："能工作的代码"不是主要目标；系统**长期结构**才是。你的最重要工作是方便未来的扩展
  - 投资心态：主动投资（为每个新类多花时间比较几种设计、写好文档）+ 被动投资（发现设计问题就修，而不是绕过）
- **10-20% 投资比例**: 将总开发时间的 10-20% 用于投资。前期项目慢 10-20%，几个月内收益显现，之后开发速度反超 10-20% 以上，投资变"免费"；坏代码库至少拖慢开发 20%

## Key Concepts
- **投资必须今天做**："等这阵忙完再清理"是滑坡——忙完这阵还有下一阵；拖延一旦开始就易永久化
- **初创公司也适用**: 代码库一旦变面条就几乎无法挽回；好/坏设计的回报来得很快，战术法可能连首个发布都加速不了；烂代码库还会赶走顶尖工程师（他们最在乎设计），推高未来成本

## Worked Example
三家公司对照：
- Facebook："Move fast and break things"，新工程师第一周即向生产环境推 commit → 代码不稳定、少注释少测试，最终文化不可持续，口号改为 "Move fast with solid infrastructure"
- Google / VMware：同期成长，强调高质量代码与好设计 → 强技术文化成为招聘顶级人才的护城河
- 结论：两条路都能成功，但在在乎设计、代码库干净的公司工作有趣得多

## Key Takeaways
1. 第一步是意识到：为快速完成当前任务而引入不必要的复杂性是不可接受的
2. 大量小额、持续的投资优于一次性巨额前置投入（后者即瀑布法）
3. 卓越设计 + 能工作，而不是能工作 + 顺便设计
4. 团队里警惕战术龙卷风：以长期产出来评价，而非短期代码量
