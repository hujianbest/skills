# Chapter 8: 降低复杂性 (Pull Complexity Downwards)

## Core Idea
模块遇到不可避免的复杂性时，通常应由模块开发者在其内部消化，而不是推给使用者——**模块拥有简单接口比拥有简单实现更重要**。大多数模块用户远多于开发者：宁可一个开发者受苦，不叫众多用户受苦。

## Frameworks Introduced
- **复杂性下拉 (pull complexity downwards)**
  - 反面冲动: 解决容易的问题，把难题抛给别人——不确定怎么处理就抛异常；不确定什么策略就导出配置参数
  - 这些做法放大复杂性：一个问题从 1 个人处理变成 N 个人处理（每个调用者都要处理异常；每个安装的管理员都要学参数）
  - 典型例子: ch6-7 的 text 类——面向行的接口实现简单但把行拆分/合并的复杂性推给所有高层代码；面向字符的接口把复杂性拉进类内，系统整体更简
- **配置参数是复杂性上推** (configuration parameters)
  - 辩护理由: 用户更懂自己的域（如某些请求更紧迫，该由用户设优先级）——这种情况合理
  - 更多时候是逃避: 用户/管理员根本定不出正确值；或者系统稍加实现就能自动算出。例: 重试间隔可做成配置项，但协议可以自己测量成功请求的响应时间×倍数——还自动适应环境变化，而配置会过时
  - 判据: 导出参数前问"**用户（或高层模块）能定出比我们在此处更好的值吗？**"能→暴露；不能→内部解决+自动默认值
- **理想**: 每个模块应**完整地**解决一个问题；配置参数=不完整的解决方案

## Key Concepts
- **下拉的适用条件**（防止走极端——把整个应用拉进一个类）: (a) 复杂性与该类现有功能密切相关 (b) 下拉后应用其余多处显著简化 (c) 下拉简化了类的接口。目标是**系统整体**复杂性最小
- **反例**: 把 UI 知识（退格键）拉进 text 类不满足 (a)(b)——只会造成信息泄漏（见 ch6）

## Key Takeaways
1. 开发模块时寻找机会：自己多吃一点苦，换用户的苦少很多
2. 抛异常和导出配置参数是最常见的两种"复杂性上推"，都应先自问能否内部消化
3. 能自动确定的值就不要配置化；必须配置的也要给出自动的合理默认值
