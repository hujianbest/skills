# Chapter 19: 软件发展趋势 (Software Trends)

## Core Idea
用本书原则逐一检验近几十年的流行趋势（OOP 继承、敏捷、单元测试、TDD、设计模式、getter/setter），问同一个问题: 它是否真的降低了大型软件系统的复杂性？

## Frameworks Introduced
- **面向对象与继承 (OOP & inheritance)**:
  - **接口继承** (只定义签名): 正面——同一接口复用于多种用途、实现越多接口越深（必须抓住各实现的共性、回避差异 = 抽象的本质）
  - **实现继承** (继承默认实现): 双刃——减少变更放大（免复制），但父子类共享实例变量 → 类层次内**信息泄漏**，改父类要查所有子类、覆盖方法要读父类实现，最坏需通晓整棵层次树 → 用前先考虑**组合**替代；必须用时把父类状态与子类状态分离（某些变量仅父类方法管理、子类只读）
  - OOP 机制不保证好设计——浅类/复杂接口/暴露内部状态的 OOP 一样烂
- **敏捷开发**: 增量迭代 ✓ 与本书一致（初始设计必有错，增量纠错）。风险: 敏捷聚焦**功能**而非抽象、鼓励推迟设计 → 战术化。修正: **增量的单位应是抽象，不是功能**——某抽象被需要时一次把它干净设计完（含适度通用），不要零碎生长
- **单元测试**: 正面——测试是重构的安全网；无测试套件的系统里没人敢重构 → 复杂性累积、设计错误永不被纠正。案例: Tcl 解释器换字节码编译器（影响核心引擎每一处），靠单元测试套件 alpha 后只出 1 个 bug
- **测试驱动开发 (TDD)**: 作者**反对**用于开发——注意力锁在"让下一个测试通过"= 纯战术编程、过于增量、没有做设计的时机。唯一例外: **修 bug 先写失败测试**（保证真的修好了，否则新测试可能根本触发不了该 bug）
- **设计模式**: 正面——共识方案通常干净、自研很难超越。最大风险: **过度套用**——模式不合身时硬套不如量身定制；"模式好"不等于"模式越多越好"
- **getter/setter**: 反面模式——若必须暴露实例变量可以加，但**最好根本不暴露**；暴露实现数据违反信息隐藏、getter/setter 是典型的浅方法（一行代码撑起一个接口元素），Java 社区对其过度使用正是"模式被神化后滥用"的例证

## Key Concepts
- **评估任何新范式的统一提问**: 它真的帮助最小化大型系统的复杂性吗？许多听起来美好的提案深究后让复杂性更糟

## Key Takeaways
1. 接口继承放心用；实现继承先想组合
2. 增量开发 ✓，但增量单位 = 抽象；TDD 单位 = 功能，故冲突
3. 单元测试是重构的先决条件——战略编程的基础设施
4. 模式、语言机制都是工具不是目标，一律过"复杂性检验"
