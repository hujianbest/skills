# Chapter 5: 信息隐藏 (和泄漏) (Information Hiding and Leakage)

## Core Idea
实现深模块最重要的技术是**信息隐藏**：每个模块封装少数代表设计决策的知识，深埋在实现中、不出现在接口里。其反面——同一知识出现在多个模块——是软件设计中最重要的红旗之一。

## Frameworks Introduced
- **信息隐藏 (information hiding)** (源自 Parnas 1972)
  - 每个模块封装的知识 = 机制的实现细节（数据结构+算法，也可含低层细节如页大小、高层假设如"多数文件较小"）
  - 降复杂性的双重机制: ①简化接口（认知负荷↓）②隔离变化（该知识的依赖只在一个模块内，演化只影响一处）
  - 注意: private ≠ 信息隐藏——getter/setter 照样把私有变量的性质与用法暴露得和 public 一样
  - **部分隐藏也有价值**: 只被少数用户需要、通过单独方法访问、常见用例中不可见 → 依赖少于全暴露
- **信息泄漏 (information leakage)** ——红旗
  - 定义: 一个设计决策反映在多个模块中（接口中出现 = 定义上的泄漏；两个类共享同一文件格式知识 = **后门泄漏 back-door leakage**，比接口泄漏更隐蔽更危险）
  - 处方: 问"如何重组这些类，让这份知识只影响一个类？"——合并受影响类，或抽取只封装该知识的新类（前提是能找到从细节抽象出的简单接口，否则只是把后门泄漏换成接口泄漏）
- **时间分解 (temporal decomposition)** ——红旗
  - 系统结构对应操作发生的时间顺序（先读文件、再修改、后写文件 → 三个类）。读和写共享文件格式知识 → 泄漏
  - 处方: 按执行任务所需的**知识**分解模块，而不是按执行顺序；顺序会体现在某处，但不应体现在模块结构上
- **过度暴露 (overexposure)** ——红旗: 常用功能的 API 强迫使用者了解罕见功能（如要求调用者手工指定 HTTP 响应版本号——它本应与请求自动对应）

## Key Concepts
- **默认值 (defaults)**: 部分信息隐藏的范例——正常情况下调用者不知道默认项的存在；少数需要覆盖时才感知
- **类内信息隐藏**: 私有方法各自封装一份信息/能力；尽量减少每个实例变量被使用的位置数
- **隐藏的前提**: 信息确实不需要在模块外被用到。若外部需要（如影响性能的配置参数），必须暴露——目标是**最小化**模块外需要的信息，能自动调优就别暴露参数

## Worked Example
学生 HTTP 服务器项目的三类错误：
1. 两个类分别"读取请求"和"解析请求"——时间分解。读请求必须解析 Content-Length 才能知道总长 → 两类都懂 HTTP 格式，解析代码重复 → **合并为一个类**：知识隔离、接口更简（一个方法）
2. `getParams()` 返回内部 Map 引用——暴露内部表示，改表示就改所有调用者，还要求调用者知道不能改这个 Map → 改为 `getParameter(String name)` / `getIntParameter(String name)`：更深、隐藏表示、代理解码
3. 响应的协议版本/Date 头要求调用者显式指定 → 应由 HTTP 库自动提供

一般主题：**把类稍微做大一点常能改善信息隐藏**——①聚齐某能力的全部相关代码 ②抬高接口层级（三个步骤方法 → 一个整体方法）。

## Key Takeaways
1. 设计新模块时先问：哪些知识可以藏进这个模块？能藏的越多，接口越简、模块越深
2. 对信息泄漏保持高度敏感——尤其是后门泄漏
3. 不要按执行顺序分解系统；按知识分解
4. 暴露内部数据结构（返回 Map/List 引用）是最常见的泄漏形态
