# Chapter 15: 先写注释 (Write The Comments First)

## Core Idea
写注释的最佳时机是**写代码之前**——注释先行的开发顺序让文档成为设计过程的一部分：注释更好、**设计更好**、写文档甚至变得有趣。

## Frameworks Introduced
- **迟到的注释是坏注释**: "等代码稳定再写" → 永远等不到稳定 / 稳定时已海量堆积 / 心理上代码"已完成"、只想草草应付 / 设计记忆已模糊 → 注释退化为复述代码、丢失最该记录的设计思想
- **注释先行的顺序 (comments-first workflow)**:
  1. 新类: 先写**类接口注释**
  2. 写最重要公有方法的**接口注释 + 签名**，方法体留空；迭代到基本结构感觉对了
  3. 写最重要的类实例变量的**声明 + 注释**
  4. 填方法体，按需补实现注释；过程中新增的方法先写接口注释、变量声明同时写注释
  - 代码完成时注释同步完成，永无积压
- **注释是设计工具 (canary in the coal mine)**:
  - 注释是**完全捕获抽象的唯一途径**；先写抽象注释可在写实现前评审、调整抽象
  - 接口注释**简短而完整**地描述了用法 = 方法接口简单；注释必长必繁 = 接口复杂
  - 接口注释必须罗列实现的主要特性 → 方法浅
  - 变量需要长注释 → 变量分解不对
  - 红旗: **难以描述 (hard to describe)**——写不出简单又完整的注释，说明被描述者的设计有问题
  - （注释作为度量指标的前提: 注释本身完整清晰）

## Key Concepts
- **成本核算**: 敲代码+注释合计约占开发时间 10%，注释至多一半 → ~5%；延迟写省不了多少，而注释先行让抽象先稳定、编码期返工更少——总耗时可能反而更短
- **早期注释有趣**: 注释是记录与检验设计质量的手段；用最少词汇完整清晰表达的设计是自豪感的来源

## Key Takeaways
1. 顺序反转: 类注释 → 方法注释+签名 → 变量注释 → 方法体
2. 把"注释写不顺"当作免费的设计告警，先修抽象再继续
3. 别用"代码还在变"当借口——接口层面的抽象恰恰要先于代码稳定
