# Cheatsheet — A Philosophy of Software Design

## 设计决策规则 (作者 15 条原则的操作化)

| # | 决策规则 | 依据 |
|---|---|---|
| 1 | 复杂性零容忍——每一点"就加一点点"都要拒绝 | 复杂性递增 |
| 2 | "能跑"不收工——问"这是干净设计还是刚好能跑" | 战略编程 |
| 3 | 持续投入 10-20% 时间做设计投资 | 投资心态 |
| 4 | 评价模块先问: 接口小还是功能大？ | 深模块 |
| 5 | 最常见用法必须是最简调用 | 接口设计 |
| 6 | 接口简单 > 实现简单 | 复杂性下拉 |
| 7 | 功能专用、接口通用 | 适度通用 |
| 8 | 通用机制里发现专用代码 → 上提拆分 | 通用/专用分离 |
| 9 | 穿层而下抽象必须变；没变是坏味道 | 不同层不同抽象 |
| 10 | 难题模块内消化，别抛给调用者 | 复杂性下拉 |
| 11 | 定义异常前先问: 语义能否重定义使它不存在？ | 错误消除 |
| 12 | 重大决策强制对比 2-3 个根本不同方案 | 设计两次 |
| 13 | 注释只写代码看不出来的东西 | 注释原则 |
| 14 | 为易读设计，不为易写设计 | 明显性 |
| 15 | 增量单位 = 抽象，不是功能 | 演化原则 |

## 红旗速查 (看到即停，寻找替代设计)

| 红旗 | 信号 | 章 |
|---|---|---|
| 浅模块 | 接口复杂度 ≈ 实现复杂度 | 4 |
| 信息泄漏 | 同一知识出现在多个模块 | 5 |
| 时间分解 | 模块结构 = 执行顺序 | 5 |
| 过度暴露 | 用常用功能得先懂罕见功能 | 5 |
| 直通方法 | 方法只转发同签名调用 | 7 |
| 重复 | 同一代码模式反复出现 | 9 |
| 专用-通用混合 | 通用机制里混特定用例代码 | 9 |
| 连体方法 | 不看 B 的实现就读不懂 A | 9 |
| 注释复述代码 | 只看旁边代码就能写出该注释 | 13 |
| 实现污染接口 | 接口注释讲实现细节 | 13 |
| 含糊命名 | 名字泛到可指多种事物 | 14 |
| 难以取名 | 找不到精确直观的名字 → 设计问题 | 14 |
| 难以描述 | 简单又完整的注释写不出来 → 抽象问题 | 15 |
| 代码不明显 | 快速阅读猜不出行为 | 18 |

## 快速决策树

- **要抛异常？** → 语义可重定义？→ 是: 定义不存在 / 否: 外部需要知道吗？→ 否: 低层屏蔽或崩溃 / 是: 多处同类？→ 是: 高层单点聚集 / 否: 正常抛出
- **两个功能合还是分？** → 共享知识 or 合并简化接口 or 消除重复？→ 任一成立: 合并；都不成立但相关？→ 谨慎: 光标+选区教训 = 分开
- **要拆方法？** → 只因长度？→ 不拆；能提取干净通用的子任务？→ 拆；拆完需要父子对照阅读？→ 撤回（连体）
- **要建装饰器/包装类？** → 先问: 加进底层类？并入用例？合并既有装饰器？做成独立类？——四问有解就不用装饰器
- **要导出配置参数？** → 用户能定出比我更好的值？→ 否: 内部解决+自动默认 / 是: 暴露，但给自动默认
- **性能优化？** → 先测量定位 → 有根本修复（缓存/算法）？→ 用之；没有 → 关键路径重构（理想代码法）→ 复测无收益即回退

## 关键阈值与默认值

- 设计投资: 总开发时间 **10-20%**（前期慢 10-20%，数月内反超）
- 注释成本上限: ≈ 开发时间 **10%**（敲代码本身也只占 ~10%）
- 坏代码库拖累: 至少 **-20%** 开发速度
- 哈希表 vs 有序 map: **5-10x** 速度差，不需要排序就选哈希
- 忽略性能的后果: 系统可慢 **5-10x**，且后期难救
- 警惕"没被执行过的代码是不能工作的代码"——>90% 分布式系统灾难性故障源于错误处理

## 命名速查

- 布尔名 = 谓词 (`cursorVisible` ✓ / `blinkStatus` ✗)
- 名字含糊 = 加 "of what" (`getCount` → `numIndexlets`)
- 同类多变量 = 通用名+前缀 (`srcFileBlock`/`dstFileBlock`)
- 循环: 最外层 i、嵌套 j；声明-使用距离越远名字越长
- 取名困难 → 先怀疑实体定义不清，拆变量/改设计
