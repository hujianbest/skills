# 一点写代码的心得（六）：Agent的最小Harness怎么搭

> [上篇文章](https://3ms.huawei.com/km/blogs/details/22254061?l=zh-cn)聊到了 AI Coding 时代的软件工程，也从我自己做摄影网站的折腾经历里，聊了聊为什么“老古董”的软件工程方法在 AI 时代反而成了绝世基本功。
> 
> 文章发出来后，内网和微信上不少兄弟跑来找我聊。有同学说：“老胡，道理我都懂了，但看你搞的 Harness Flow 又是 SDD、又是 TDD、又是多 Agent 审查的，太重了。如果我手里就一个小项目，到底该怎么搭一个**最小、最顶用**的 Harness？”
> 
> 这话说得极在理。今天咱们不聊大而全的流水线，就聊聊怎么花半天时间，给你的项目搭一套**最小可用（MVP）的 Harness**。

做技术的人都有个毛病：一听到新概念，就容易往复杂里整。

去年年底 OpenAI 和 Anthropic 连续发了几篇谈 Harness Engineering 的硬核文章，很多人一读，直接被里面的专业词汇绕晕了：状态机、规划器、动态上下文修剪、评估门禁……仿佛不写个几千行 Python 编排框架，都不好意思叫 Harness。

其实真没那么玄乎。**Harness 的本质，就是你给 AI 圈出来的“工作现场纪律”。**

当年我们在公司做 30 万行大型重构的时候，新员工进组的第一天，老导师绝不可能丢给他一本厚如字典的架构规范。通常就带他看三样东西：代码在哪编译、提交前跑什么测试、遇到不懂的问题去问谁。

给 Agent 搭建工程现场，完全是一模一样的道理。

---

## 1. 为什么你的 Agent 总在“好心干坏事”？

如果你平时常用 Cursor、Claude Code 或者其他智能体写代码，大概率经历过这种血压飙升的时刻：

你给它提了一个看似很简单的小需求：“把这个列表页的筛选按钮改成支持多选”。

它接单后屏幕刷刷飞滚，五分钟改了十二个文件。然后很有礼貌地告诉你：“已为您完成多选支持，并顺手重构了全局状态管理，优化了网络请求缓存机制。”

你心里咯噔一下，赶紧把项目跑起来。果然：多选按钮能点了，但分页失效了；列表能刷出来了，但详情页直接白屏了。

### 1.1 执行力太强的烦恼

这时候咱们很容易骂模型笨，抱怨它上下文窗口不够大。

但如果你仔细看它的改动，单看每个函数，它写得其实都挺规范的，甚至比很多初级工程师还要规矩。**问题不在于它不会写代码，在于它太能写了，而且它看不见全局。**

AI 改代码时，它的视野被死死局限在当前的 Prompt 和几个关联文件里。它在局部做了一件自以为正确的事，但放进你原本的系统里，可能直接把隐式契约给干翻了。

> **AI 就像一个精力过剩、但对你的系统历史一无所知的名校实习生。**
> 
> 你让他修个水龙头，他觉得你厨房的水管走线不够优雅，趁你午休把整面墙的瓷砖都砸了重铺。热情可嘉，但让人崩溃。

### 1.2 口头完成不是真完成

AI 还有一个特别折磨人的习惯：**犯了错还极度自信。**

它特别擅长在单测没跑全、编译没通过、甚至页面压根起不来的情况下，言之凿凿地宣称“功能已完美实现”。它能把一个满是漏洞的半成品，总结得像年终述职 PPT 一样漂亮。

你要是没有一套规矩去卡它，你就只能自己一遍遍肉身去点按钮、抓请求、擦屁股，把省下来的时间全赔在排障里。

## 2. 最小的 Harness，核心就三件事

别去迷信那些花哨的框架，回归工程常识，一个能跑通真实任务的最小 Harness，核心其实就三句话：

- **看得见**：别让 Agent 瞎猜；
- **控得住**：一次只准动一块地方；
- **验得实**：别听它吹牛，拿证据说话。

### 2.1 看得见：给地图，别给百科全书

很多人第一天给项目加规则，最喜欢干的一件事，就是把公司所有的规范、自己踩过的所有坑，一股脑全写进 `AGENTS.md`。动辄上千行，恨不得把软件工程导论都塞进去。

结果呢？Agent 读完直接消化不良，注意力被稀释殆尽，真正要紧的规矩一条没记住。

**根指令文件应当是地图，而不是小说。**

它只需要控制在一两百行以内，清晰地告诉 Agent 三件事：开工第一步干嘛、改代码有什么不可触碰的红线、遇到架构疑难去哪个具体文档找。至于详细的 API 定义、架构原则，分门别类丢到 `docs/` 目录里，让它需要的时候按图索骥去读。

### 2.2 控得住：一次只端一个盘子

老程序员带徒弟，最关键的一条是“控制作业面”。

给 Agent 分派任务，千万不要给一个宏大的愿景。把需求拆碎，拆成一个个**具备端到端可见行为的小切片**。

比如不要写“优化登录模块”，要写成“在输入错误密码时，输入框下方标红显示提示语，并保持用户名不清空”。

一次会话，只准它认领一个切片。不管它多么热心想顺手帮你改点别的，只要不在当前切片里的改动，全部打回。**把任务切小，是保护系统架构最便宜的手段。**

### 2.3 验得实：把完成定义收回事实

在没有验证之前，AI 嘴里的“完成”一文不值。

什么叫完成？必须由事实裁定。

单元测试跑了吗？接口返回 200 了吗？浏览器无头截屏里元素渲染正常吗？日志里有没有报错？

只有当客观命令吐出了无异常的输出，它才有资格打上“已完成”的标签。

## 3. 四个文件，搭起你的最小工程现场

如果明天你想在自己的项目里落地，不用大动干戈，在代码仓库根目录配好这四个文件，你的 Agent 表现立马会脱胎换骨。

```
my-project/
├── AGENTS.md            # 现场总则（地图）
├── feature_list.json    # 任务账本（边界）
├── init.sh              # 统一体检入口（地基）
└── progress.md          # 交接班日志（外置记忆）
```

### 3.1 AGENTS.md：清晰的开工令

别写大段散文，全部写成直截了当的**行为指令**。

```markdown
# 工程现场核心纪律

1. **开工检查**：每次启动任务，先执行 `./init.sh`。基线红灯时禁止添加任何新业务代码！
2. **单一职责**：每次只允许认领 `feature_list.json` 中一个状态为 `failing` 的功能，禁止跨范围修改。
3. **完成标准**：声明完成必须附带真实测试运行成功的日志输出证据，禁止口头汇报。
4. **遇阻刹车**：如果改动涉及到公共契约修改，必须先停下向人类确认，禁止自行发挥。
```

把最重要的纪律置顶，简单、干脆、没有歧义。

### 3.2 feature_list.json：拿证据说话的任务清单

不要只写简单的 TODO 列表，那太容易被 Agent 浑水摸鱼了。任务项里必须包含**验证方式和证据槽位**。

```json
{
  "features": [
    {
      "id": "F-01",
      "desc": "用户点击新对话按钮后，左侧栏生成新会话并在列表第一项高亮",
      "status": "in_progress",
      "verify_command": "npm run test:e2e -- chat-create",
      "evidence": ""
    }
  ]
}
```

在规则里卡死一条：只有当 `verify_command` 跑通，且将实际输出贴进 `evidence` 字段后，`status` 才允许由人工或脚本改成 `passing`。

### 3.3 init.sh：别在烂地基上盖楼

很多时候 Agent 把项目改崩，是因为它刚进场时，项目本身就是坏的。它在红灯的基线上继续写，最后所有问题搅和成一团乱麻。

搞一个极简的初始化体检脚本：

```bash
#!/bin/bash
set -e

echo "=== 检查项目基线环境 ==="
npm ci
npm run lint || { echo "❌ Lint 未通过，现场有遗留代码坏味道"; exit 1; }
npm run test || { echo "❌ 单测未通过，地基已损坏，请先修 Bug"; exit 1; }

echo "✅ 基线健康，允许开工！"
```

只要 `./init.sh` 报错，立刻终止一切新功能的开发。这条规则看着笨拙，但在实战中能帮你挡掉 80% 的返工灾难。

### 3.4 progress.md：数字交接班日志

长任务不可能在一个 Context 窗口里跑完。每一次 Context 窗口重启，Agent 就会经历一次“宿醉”。

为了不让下一轮 Agent 陷入茫然，必须在每轮收工前强制它写**交接日志**：

```markdown
### 2026-06-09 交接记录
- **本轮完成**：完成了 F-01 的接口实现与组件绑定。
- **验证记录**：运行了 `npm run test:e2e -- chat-create`，全部绿灯通过。
- **遗留风险**：极端断网情况下的重试未做防御。
- **下轮第一步**：直接去接 F-02，不要再动 `Sidebar.tsx`。
```

这就好比工厂倒班，白班师傅走之前把仪表盘状态和未完工零件交代得清清楚楚，夜班师傅接手就能立马干活。

## 4. 几个亲身踩过的血泪坑

这套东西看着极简，但自己在项目里折腾时，有几个坑极其容易掉进去：

### 4.1 把功能清单和进度日志混着写
功能清单（`feature_list.json`）是严谨的状态机，进度日志（`progress.md`）是叙事性的交接。如果两个地方都写状态，一旦出现冲突，AI 就会挑对自己最省事的那条去理解，瞬间钻空子。

### 4.2 迷信“自我评审”
“让 Agent 写完代码，再让它自己 Review 一遍”——听起来很美，但千万别当真。
自己审自己的代码，谁都会放水，AI 更是如此。在我的 Harness Flow 里，我宁可另起一个干净的窗口作为 Evaluator，或者直接用静态 linter 和单元测试这种无情工具来把关。

### 4.3 收工时不打扫战场
如果每轮会话结束，都留下一堆打印的临时日志、没清理干净的临时 mock 文件，两三轮下来，项目代码里就会长出一层油腻腻的 AI 废料（AI Slop）。
像厨房台面一样，每次收工前花一分钟把临时代码清干净，是给下一轮留活路。

## 5. 总结

从第一篇聊到现在，很多朋友问我：大模型进化得这么快，以后模型推理能力逆天了，上下文有一千万了，我们今天费劲巴拉搭的这套 Harness 还有意义吗？

我的看法依然很笃定：**模型越强，工程现场的价值越高。**

更强的模型，只会让它打字更快、思维更广阔。但只要软件依然要面对现实业务的千头万绪，只要我们依然要在时间跨度里维护代码，**定义完成、限制范围、度量质量的权力，就永远握在工程师手里。**

模型是跑马场里烈性的千里马，而 Harness 就是我们手里的缰绳与铁轨。

把你的工程审美和常识固化成一套清爽的现场纪律，看着它在你的轨道上不知疲倦地向前奔跑。这，也许就是这个时代属于我们软件工程师最踏实、最惬意的快感。
