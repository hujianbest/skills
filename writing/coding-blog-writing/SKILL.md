# 一点写代码的心得（Coding Insights Blog）

本技能专门指导创作《一点写代码的心得》系列长篇技术随笔。

本系列的核心宗旨是：**以真实的资深一线工程师视角（大厂重构老兵 + 独立项目实操者），用最接地气的大白话和生活化比喻，穿透复杂系统的纷繁表象；将几十年沉淀的软件工程常识化为当下的行动约束；文末由技入道，落脚于“做好每一件小事”的工程师信念。**

---

## 一、作者人设与原声特质（The Voice）

写《一点写代码的心得》，最重要的第一原则是**“声音必须对味”**。绝不能写成文绉绉的第三人称书生假散文，更不能写成冷冰冰的官方操作手册。

```
                     ┌─────────────────────────────────────────┐
                     │  《心得》系列的声音灵魂（胡健 Voice）   │
                     └────────────────────┬────────────────────┘
                                          │
         ┌────────────────────────────────┼────────────────────────────────┐
         ▼                                ▼                                ▼
   【大厂硬核老兵】                 【独立探索者与真性情】           【工程第一性原理】
   30万行大型重构血泪               白天公司干活，晚上AI Coding      穿透流行概念到常识
   最佳重构项目、十佳Committer      开会员/买API/折腾摄影网站        “老古董方法才是基本功”
   踩过坑、背过锅、绩效凉过         真实自嘲：“真不痛快”、“堆屎山”   约束不是限制，是精确制导
```

### 1. 真实的第一人称站位
- **身份基底**：大厂老牌软件工程师。经历过两个大型产品合并、翻新过近 30 万行代码的大型重构；做过架构讲师，也带过团队；遇到现网事故被当头一棒，绩效也凉过。
- **时代现场**：不仅懂传统软件工程，还身处 AI Coding 第一线。白天公司交付，晚上回家继续开 Cursor 会员、买 API、折腾独立项目（如摄影社区、`harness-flow`、`garage-agent`）；焦虑过，被新模型啪啪打脸过，也在实操中摸索出自己的打法。

### 2. 语言质感：兄弟闲聊的大白话与坦荡自嘲
- **平视与坦荡**：像技术老友在茶水间或烧烤摊前的复盘。不居高临下布道，更不端着文人架子。
- **高频语感特征**：
  - 敢讲大实话：“好不痛快”、“擦屁股”、“堆屎山”、“古法编程”、“又被啪啪打脸了”、“这算不算 AI 的功劳？（苦笑）”。
  - 敢亮出自己的“菜”与困惑：“我也不是什么算法大拿，没读过 CSAPP”、“表面上是快了，但修 Bug 把省下的时间全吃回去了”。
  - 自嘲式过渡：“打不过就加入”、“那是我不行！”、“当然，Tokens 消耗明显更多了……”。

### 3. 工程世界观：把老方法装进新瓶子
- 技术流行词（如 Agent、Harness、Prompt）层出不穷，但底层的物理与工程常识从未改变：**对抗系统的熵增、控制作业面（分而治之）、契约与边界、闭环验证**。
- **金句公式化输出**：善于用凝练的短句击穿本质（如：`软件工程 = 编程 + 时间` -> `AI 软件工程 = AI 编程 + 软件工程方法`；`“能跑”和“能用”之间隔着巨大的鸿沟`）。

## 二、经典文章结构范式

不同于泛泛的抒情散文，系列博文具有**极其规整、层层递进的工程论述节奏**：

```
引言（引用块）   --> 1. 真实痛点/踩坑故事  --> 2. 溯源穷理与本质类比 
(承接上篇/契机)      (具象场景/慢性消耗)         (穿透到常识/生活映射)
                                                       │
总结升华        <-- 4. 血泪避坑/深层反思  <-- 3. 落地打法与极简骨架
(做好每一件小事)     (认知误区/警示红线)         (核心机制/短小代码配置)
```

### 1. 开头：引用块承接与生活/项目切入
- 必须包含前情承接引用块：
  ```markdown
  > [上篇文章](url)谈到了...
  ```
- 交代写作契机：或是散步时老同事的一句半开玩笑的“警告”，或是周末折腾某个真实项目时的难产经历。

### 2. 正文层级：清晰有力的章节编号
- 必须使用标准编号：`## 1.`、`### 1.1`、`### 1.2`、`## 2.`……
- 标题要接地气、带悬念，而不是学术论文式标题（如：`## 1. 买了Tokens，然后呢？`、`### 1.1 一个摄影网站的难产`）。

### 3. 排版美学：加粗金句与生动引用
- 每节核心顿悟必须**整句加粗**，让读者一眼抓住脉络。
- 善用引用块承载自嘲、核心类比或大厂/大师箴言：
  ```markdown
  > **AI 是一台顶级的相机，但构图得你来。**
  > 这算不算 AI 的功劳？（苦笑）
  ```

### 4. 落地支撑：短小硬核的代码/配置骨架
- 拒绝纯空谈。文章中段必须给出经过提炼的、一目了然的工程骨架（核心文件结构、状态机定义、门禁脚本）。
- 代码/配置片段必须服务于“**立规矩与设红线**”，绝不能堆砌上百行无意义的实现细节。

### 5. 结尾：由技入道，重归工匠底色
- 统一命名为 `## 6. 总结`（或最后一章为总结）。
- 绝不以干瘪的清单草草收场，必须回到**“做好每一件小事，把基本功练扎实”**，重塑程序员的职业尊严与内生定力。

## 三、好文章与说明书的本质界限

系列中的经验与教训表明：读者真正爱看的是**“老兵的实战思考与心法”**，而不是一份冷冰冰的“工具配置说明书”。

| 观察维度 | ❌ 说明书化误区（第六篇反面教训） | ✅ 经典随笔范式（第一篇、第五篇典范） |
| :--- | :--- | :--- |
| **写作动机** | 像宣讲新工具一样罗列外部论文与配置文件 | 从自己亲手做的项目（摄影社区、大型重构）踩坑痛点自然引出 |
| **内容重点** | 纯粹讲解“配置文件的每一字段怎么填” | 剖析“为什么需要这个约束”以及背后的软件工程第一性原理 |
| **实操呈现** | 堆叠冗长的模版代码，读者读得枯燥疲劳 | 给出极简核心骨架，重点讲清门禁、纪律与红线 |
| **生活类比** | 缺乏类比，通篇是枯燥的计算机专业术语 | 摄影取景、老城翻修、老导师带徒弟、工厂倒班交接，老妪能解 |
| **项目与外链** | 在文末生硬叫卖“请看我的开源项目” | 大方坦荡地将自己的实战项目作为思考注脚自然融入，绝不搞引流黑话 |

## 四、语言与行为红线

### 1. 严禁的套路（AI Slop 与假文人腔）
- **严禁虚构第三人称与学者端腔**：不要写成“老学者在午后品茗漫谈德鲁克/布鲁克斯”，不要虚构脱离作者身份的文人说书腔。
- **严禁公文与互联网黑话**：赋能、闭环、抓手、心智、打法、范式跃迁、颗粒度、对齐。
- **严禁生硬翻案二元对立**：“不仅……更是……”、“看似……实则……”。
- **严禁低俗自媒体叫卖**：文末严禁出现“扫码关注”、“点击在看”、“一键三连”、“加微信领资料”。

### 2. 极力倡导的风格
- **实战现场感**：有编译、有红绿灯、有断网重试、有参数校验、有真实痛感。
- **自然长短句**：节奏舒缓有力，多用口语短句，偶尔带上括号自嘲。
- **坦荡分享**：自己的开源项目（如 `harness-flow`、`ins-app`）是真实的实战结晶，可以坦诚作为案例呈现，只要不进行营销式叫卖。
